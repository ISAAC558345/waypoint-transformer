## 1. 冻结配置和收益规则

低层从 `phase6g_seed0.pt` warm-start。动作仍是 `delta = 0.25 * tanh(pre)`，加到 `fly_toward` 上，再做单位步截断和 `SafetyProjector`。奖励仍是

`served_bits / 1e6 - 0.05 * c_project - 0.01 * c_residual`。

每个环境步只用该步实际交付的比特。15 步窗口总量只作为审计字段，不进入 Actor，也不当作当前步的即时奖励。窗口结束时 `done=1`，价值引导不跨到另一条已记录状态。Critic 宽度与冻结 checkpoint 一致，因此直接复用了其中的 critic。

训练场景是 321000–321095。开发验证是 321096–321127。评估时高层重新调用方案 C 和 `G1_RATE k=6`。PPO 保持 rollout 48、4 个环境、4 个 minibatch、4 个 epoch、学习率 3e-4、clip 0.2、value 0.5、entropy 0.01、梯度裁剪 0.5。每个种子 80 次更新。

收益规则在看到训练结果之前就固定为：3 个种子里至少 2 个满足开发验证闭环 payload 均值大于 0、10000 次 bootstrap（种子 0）的 95% 区间下界大于 0、安全违规率不超过基线加 0.02、不完整 episode 为 0，并且收益不是由单个场景撑起来的。固定 assignment 的窗口交付单独报告，不参与这个判定。

## 2. 方案 C 任务数据

数据集由正式方案 C 在冻结确定性低层上的真实决策生成。每个决策保存场景、时间、场景种子、决策前状态、UAV 与浮标位置、队列、合法 `k=6` 候选池、方案 C 选出的 assignment、TaskOption、剩余 hold、SINR、速率、干扰，以及随后真实执行的窗口交付。`k=5` 均匀样本只用于和 Phase-6I-Q 对照，没有进入训练。

训练 96 个场景、384 个决策；开发验证 32 个场景、128 个决策。决策时刻是 0、15、30、45。前三个窗口各 15 步，最后窗口 3 步。相邻窗口首尾相接。每个场景的窗口交付之和等于该场景的累计 payload。

检查在训练前完成，并且是把记录写盘后再读回做的：

| 检查 | 训练 | 开发验证 |
| --- | --- | --- |
| 行数 / 场景 | 384 / 96 | 128 / 32 |
| 方案 C 重新选择后 assignment、候选数和池哈希一致 | 384 | 128 |
| TaskOption 与 `make_option` 一致，hold 从 15 开始 | 通过 | 通过 |
| 计账与 `served_bits`、payload 一致 | 通过 | 通过 |

用冻结 Actor 把全部训练窗口按记录状态重放，交付与采集时的比特差为 0。开发验证窗口的重放差最大不到 1 bit。第一次写盘时，决策前环境里的旧 assignment 覆盖了方案 C 选出的 assignment；修复时用记录的 score index 从候选池取回所选 assignment，再对全部 512 个决策重新调用 `select_assignment`。上表是修复后的结果。修复没有改高层，也没有改环境动力学。

## 6. 结论

任务数据集和训练过程是完整的。开发验证上的闭环交付没有形成可靠改进：只有种子 0 的均值为正，它的区间跨过 0；种子 2 的区间整个为负。固定窗口对照同样没有给出三个种子一致的正收益。因此保留原始 MAPPO-V2。

产物在 `results/phase6ir_scheme_c_align/`：`dataset/train.npz`、`dataset/eval.npz` 及两份 manifest、`dataset_stats.json`、`training_curve.csv`、`summary.json`、`scenario_rows.json`、`failure_cases.json` 和三个 checkpoint。本阶段在此停止，不修改正式 Planner，也不进入高低层联合训练。

单元检查 `tests.test_phase6ir_scheme_c_align` 通过。全库约 899 个测试文件没有在本阶段重跑。
