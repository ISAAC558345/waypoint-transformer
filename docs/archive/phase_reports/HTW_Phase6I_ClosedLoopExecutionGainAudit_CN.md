## 3. 实际新增 payload

交付量是 15 步 `payload_increment_bits` 的和。窗口开始时累计 payload 置 0，所以增量就是窗口结束时的 `payload_bits`。两侧的这个等式在 16 个状态上都成立，误差不超过环境容差。

最大正差是 322062 的 +3,480,491 bit。最大负差是 322053 的 -3,481,565 bit。正负两边的幅度接近，平均值没有代表典型场景。

## 4. 置信区间与正负分布

统计单位是场景。每个场景只有一个 t=15 决策，执行器没有抽样，所以每个场景一条配对差。置信区间是这 16 个数的配对 bootstrap，10,000 次，种子 0，取 2.5% 和 97.5% 分位。这个规则在跑实验之前已经写进协议。

95% 区间是 [-535,991, +1,190,332]。下界小于 0，上界大于 0。按 1 bit 计，9 个场景为正，0 个持平，7 个为负。

## 5. SINR、干扰、服务进度与收益

两侧的有效服务步数几乎一样：G1 平均 70.2 个 UAV-步，方案 C 平均 69.8 个。完成 block 的窗口计数分别是 19.50 和 19.62。窗口结束时的队列总和，G1 是 21,727,818 bit，方案 C 是 21,221,594 bit。

方案 C 的窗口平均 SINR 是 0.283，G1 是 0.262。方案 C 的平均干扰也更高，0.0917 对 0.0659。SINR 差和交付差的相关系数是 0.44。首次进入 16 m 服务半径的步号在多数 UAV 上是 2 到 4，两侧常常相同。SafetyProjector 干预步数平均是 G1 8.69 步、方案 C 8.19 步，两侧都没有 idle，也没有中途改目标。

因此交付差不是“方案 C 多服务了几步”就能解释的。它和窗口内的 SINR 有同向关系，同时干扰也更高，而且 7 个场景的实际交付更低。

## 6. 计账和状态恢复

16 个状态的守恒误差最大约 2e-9 bit，低于环境容差。payload 增量与 `served_bits` 之和一致。环境随机数在 15 步内没有被消耗。评分中位耗时 0.0159 秒，单侧执行中位耗时 0.093 秒。没有非法 assignment，没有状态污染，没有非有限数值。
